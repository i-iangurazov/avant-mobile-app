# Внедрение и восстановление — для review, не выполнялось в production

Изменён один репозиторий: мобильный клиент и обслуживающий Node/PostgreSQL backend в этой ветке. Исходники общего Bazaar/POS/1C backend и его staging не предоставлены. Его production API проверялся только публичными GET. Нельзя считать локальные изменения развёрнутыми: deployed SHA неизвестен.

## Контракты и совместимость

- Auth v2: access token 15 минут, DB session + вращаемый refresh token до 30 дней. Старые stateless tokens намеренно не принимаются. Клиент и backend нужно выпускать согласованно; старые клиенты без OTP/refresh требуют обновления. Это несовместимое изменение старого auth-контракта, а не прозрачная миграция.
- POST `/auth/phone/challenge`: action register/login/phone_change/password_reset/delete; сервер связывает challenge с нормализованным номером, действием и account ID. Регистрация, первый вход legacy-аккаунта, смена номера, reset и удаление требуют соответствующего одноразового proof. Повторный обычный вход уже проверенного аккаунта — пароль. Роль не выводится из телефона.
- SMS adapter: серверный HTTPS POST в `SMS_PROVIDER_URL`, Bearer `SMS_PROVIDER_TOKEN`, `Idempotency-Key=challengeId`; JSON phone/code/action/challengeId/expiresInSeconds. Нужен собственный проверенный адаптер конкретного провайдера; это не объявление совместимости с любым SMS API. TTL 5 минут, 5 попыток, 5 отправок в час на номер, общие DB limits. Коды не логировать; секрет HMAC хранить вне клиента. Изолированный адаптер существует только в `scripts/tests/isolated-network.mjs` и отказывается работать вне тестовой БД localhost:55448/remediation.
- Admin: только активная роль БД и проверенный номер. `ADMIN_PHONE_NUMBERS` больше не предоставляет права. Публичного назначения admin нет. `scripts/admin/set-role.ts ACTOR_ID ACCOUNT_ID grant|revoke CHANGE_TICKET` требует существующего DB-admin и пишет аудит. Первый доверенный администратор создаётся отдельно оператором БД после проверки личности и одобренного change ticket, в транзакции с `granted_by`/audit; не массовым UPDATE по allowlist.
- Заказ: POST `/orders/quote` возвращает доверенный пересчёт; POST `/orders` требует clientRequestId. Цена/название берутся из `app_order_offers`, филиал — из `app_order_branches`, organization ID — только из серверной конфигурации. Количество 1..999, целое. Client price служит только проверкой устаревшего quote. Клиентские скидки/итоги/bonusAmount/org отклоняются. Другой payload того же ключа →409; одинаковый → тот же заказ. Неизвестный результат сохраняется на устройстве и повторяется с прежним body/key; 201/200 не создают второй заказ.
- Данные филиалов/предложений заполняет только доверенный inventory adapter: organization/branch/product, unit_price_minor (целые тыйыны), stock_quantity, is_active, valid_until. NULL price разрешён лишь для явно помеченного request_only. До согласования источника, SKU/branch mapping и синхронизации данные не загружаются; production остаётся закрытым для оформления. Нельзя копировать клиентскую цену в таблицу предложений. Изменение stock не должно перетирать reserved_quantity; sync, sale, cancel и expiry должны блокировать соответствующие строки в том же порядке. Политику времени резерва и сверку с POS ещё должен подтвердить владелец.
- При created заказ удерживает доступный остаток; cancelled освобождает один раз; completed расходует один раз. Старые заказы имеют inventory_held=false. Старый заказ с отсутствующим request_hash не используется для нового мутирующего повтора:409 и проверка истории. Денежного эквайринга в этом scope нет.
- Loyalty: существующие ставки/уровни/округление не изменены. Баланс выводится из реального журнала, изменения сериализуются по мастеру. Cursor pagination использует точный PG timestamp+ID. Возврат до чека →404, интеграция должна повторить его после чека; испытание повторной доставки проведено локально. Нужны согласованные retries/DLQ в POS. Отрицательный баланс после уже потраченного начисления и ставка при base=0 остаются вопросами, а не исправляются выдуманным правилом.
- Documents: оператор публикует только утверждённые версии в `app_public_documents`; одна current версия каждого kind. Анкета принимает именно текущие privacy/loyalty версии. Проекты из drafts не загружаются миграцией. Для удаления клиент подтверждает текущую deletionDocumentVersion.
- Media adapter: HTTPS `MEDIA_PROVIDER_URL` + серверный токен, `/upload` принимает id/accountId/mime/dataBase64, отвечает id/url/metadataStripped=true; `/delete` принимает id и идемпотентно отвечает deleted=true, включая уже удалённый объект. Нужен настоящий decoder/re-encoder, ограничения dimensions/pixels, удаление EXIF и подтверждённый `MEDIA_PUBLIC_HOST`. Сервер проверяет размер/signature JPEG/PNG и принадлежность зарегистрированного URL аккаунту. Тестовый ответ metadataStripped не подтверждает реальную очистку.
- Удаление: включается только после утверждения политики через ACCOUNT_DELETION_MODE=erase-all и current deletion document. Пароль + связанный OTP, реальные DELETE в БД, удаление принадлежащих фото через adapter, отзыв сессий. Чужие заявки сохраняются и отвязываются, чужие заказы/остатки не удаляются. При неудаче удаления media DB откатывается, proof нужно получить заново; provider deletion обязан быть идемпотентным. Режима юридического retention ещё нет: его нельзя молча заменить erase-all. Удаление копий у Telegram/POS, в backup и сроки их хранения требуют установленной процедуры до активации.

## Preflight и порядок

1. Назначить владельца выпуска и инцидента D01. Получить список всех потребителей общего backend, deployed SHAs, staging, договорённости SMS/media/POS. Проверить старый клиент против нового backend на staging; согласовать обязательное обновление и окно переключения. Не сохранять уязвимый auth fallback для совместимости.
2. Снять защищённый backup средствами оператора; проверить место, PITR и восстановление на отдельной БД. Сохранить контрольные количества/ledger totals по account/plumber и список активных сессий/ролей. Локальная репетиция: `evidence/database-recovery.json`, 34 таблицы, согласованный pg_dump snapshot.
3. Применить только после review: `psql "$STAGING_DATABASE_URL" -v ON_ERROR_STOP=1 -f scripts/db/migrations/20260918-production-readiness.sql`. Миграция additive, не верифицирует телефоны, не выдаёт роли, не пересчитывает баланс и не удаляет данные. Дважды проверена на baseline schema с существующим аккаунтом.
4. Загрузить утверждённые документы и доверенные branch/offer данные отдельной reviewed транзакцией; проверить организацию, цены, остатки и valid_until. Настроить секреты на сервере, HTTPS, reverse proxy и мониторинг. Никаких секретов в EXPO_PUBLIC_*.
5. Развернуть backend в staging; NODE_ENV=production требует уже существующие таблицы и не выполняет ensureSchema автоматически. Health реально запрашивает БД; без обязательных Telegram/webhook настроек возвращает503. Проверить 503 при недоступной БД и восстановление. Общий rate limit не доверяет X-Forwarded-For: за proxy пользователи могут делить IP bucket; capacity/доверенный proxy boundary нужно проверить до production.
6. Собрать клиент с явным EXPO_PUBLIC_API_URL. `npm run check:release-env` проверяет обязательную HTTPS-конфигурацию и запрещает debug/test placeholder для production EAS; сама доступность/совместимость требует staging smoke. Не полагаться на старый Metro cache при смене окружения: clean export/build, затем проверить embedded URL.
7. Пройти owner device checklist, внешние интеграции, store disclosures и review credentials. Только затем отдельное решение владельца о rollout. Здесь не выполнялись merge, push, deployment, store upload, реальные SMS, списания или production mutations.

## D01: аудит привилегий и старые сессии

Оператор выполняет read-only выборку аккаунтов с admin ролью, granted_at/granted_by и phone_verified_at; отдельно сверяет legacy allowlist с журналом регистраций/изменений номера и admin actions. Сопоставить с утверждённым списком сотрудников, проверить подозрительные чеки/возвраты/награды/назначения. Нельзя автоматически удалить совпавшие аккаунты или переписать балансы.

Для каждого подтверждённого инцидента подготовить список account IDs и affected operations, доказательства, резервную копию и одобрение владельца. Затем точечно отозвать роль/сессии audited CLI. Прежние stateless tokens станут недействительны при включении auth v2; это требует явного плана принудительного входа для всех затронутых клиентов. Сам rollout здесь не выполнен. Секрет подписи ротировать при установленном компромиссе, а не маскировать этим отсутствие проверки ролей.

## Откат

При проблеме остановить оформление/мутации через контролируемый maintenance ingress и приостановить rollout клиента. Additive таблицы/колонки сохранить; не выполнять destructive down migration. Откатить на проверенную сборку с теми же security guards или hotfix; возврат к baseline auth/доверенным клиентским ценам недопустим. Восстановление backup в production — отдельная одобренная операция с reconciliation новых заказов/ledger/outbox, чтобы не потерять операции после snapshot. Подтвердить после внедрения: чужие/admin запросы отклоняются, повтор даёт один order ID, ledger сверяется, stale tokens отказаны, approved documents доступны, один тестовый номер получает SMS, один sandbox media asset удаляется, наблюдаемость фиксирует ошибки без PII.
